# Decisions

Judgement calls made where the design was ambiguous or a choice had to be made. Newest last.

## Phase 1

**D1. npm workspaces, not Nx.** Three packages; Nx adds tooling weight without a clear win. Angular CLI and Nest CLI run per workspace.

**D2. Drizzle, not Prisma; hand-written SQL migrations.** The important parts of the schema are SQL-level — append-only triggers, GRANT/REVOKE, generated `tsvector` columns, a deferred version-chain constraint trigger, views. Drizzle is SQL-first and stays out of the way; we use it for typed queries only. Migrations are plain `.sql` files applied in order by a ~50-line migrator that records itself in the (append-only) `schema_migration` table.

**D3. "Superseded-at" is a row, not a column.** Stamping the old version with superseded-at/by/why would be an UPDATE. Instead each supersession is an insert into `record_supersession` (entity, version, superseded-by-version, at, by, reason). `record_active` and `record_archive` views join them. A deferred constraint trigger refuses any version N>1 that isn't committed together with the stamp on N−1, so history can't fork or skip.

**D4. All domain objects are versioned entities in the record.** Units, bots, operations, missions, tasks, supply and documents are not mutable tables: every change (including a bot's status) is a new version with an actor and a reason. Current state = `record_active`. Immutable things (War Diary, sitreps, working-record steps, chat, credential use, policy holds, redactions) are `record_event` rows.

**D5. Append-only is enforced twice.** (1) The API connects as `orbot_app`, which has only SELECT and INSERT. (2) Row and TRUNCATE triggers raise `OR001` for every role, including the table owner. Superusers and `ALTER TABLE … DISABLE TRIGGER` by the owner remain possible at the database level; the owner credentials are used only for migrations.

**D6. The secrets store is a separate database with its own role,** values AES-256-GCM encrypted with `ORBOT_SECRETS_KEY`, the secret's name bound as AAD. It is the one place rows change: rotating a secret overwrites the old ciphertext (keeping old secret values around would be worse than the principle-4 exception). Every store/rotate/revoke is logged in the record by name. `orbot_app` cannot connect to it (tested).

**D7. Redaction masks rather than rejects record writes.** Blocking a bot's diary entry because it pasted a token would lose the rest of the entry; masking keeps the record useful and safe. Each masking writes a `redaction.applied` event naming the detector (never the value). The redactor knows every live secret (exact match plus base64/URL/JSON-escaped variants) and also pattern-matches unknown secrets (provider token formats, PEM keys, `password=…`, URL credentials, high-entropy strings). The high-entropy detector judges path/URL segments individually so filesystem paths aren't masked. Revoked and rotated values stay known to the redactor for the life of the process.

**D8. Policy hook records holds, not every allow.** Every bot event and credential use passes through `PolicyService.check()`. Recording every allowed check would double the record without adding information (the resulting entry is the evidence it was allowed), so only refusals/escalations are written. Phase 1 has no rules.

**D9. `BotRuntime` is just `run(brief, ctx) → AsyncIterable<BotEvent>`.** Workspaces are prepared by `WorkspaceManager` (HQ needs to know who touches what for deconfliction), not by the runtime. Credentials reach a runtime only through `ctx.withCredential`, so a runtime cannot forget to record the use.

**D10. Connected repositories are always cloned.** ORBOT works from its own clone under `ORBOT_WORKSPACES_DIR/repos/<id>` and makes a worktree per task (`orbot/task-<n>`), so bot branches never touch the Commander's checkout. Worktrees are never removed.

**D11. Scenario-driven simulation.** `SimulatedRuntime` plays JSON scenarios (`happy-path`, `blocked-on-dependency`, `tests-fail`, plus test-only `rogue-leak`/`rogue-crash`). Text variation uses a PRNG seeded only by the scenario, so a scenario always plays out the same way. `ORBOT_SIM_SPEED` scales waits (0 in tests and seeding).

**D12. Operation lifecycle state machine.** Phases are Intent → O Group → Backbrief → Execution → Handoffs/Sitreps → After Action → Closed, with a rejected backbrief returning to O Group. A Frago is an event allowed in any phase before After Action, not a phase. (Encoded in `packages/shared/src/domain/operation-lifecycle.ts`; used from Phase 4.)

**D13. Auth: single Commander, signed session cookie.** Passphrase from env, HMAC-signed httpOnly cookie, `Principal { kind, id, displayName, rank? }` on every request so officers with ranks slot in later.

**D14. SCSS + CSS custom properties, no Tailwind; a script instead of Stylelint.** Tokens are the single source of truth. `scripts/check-tokens.mjs` fails CI on raw colours/lengths in component styles (media-query breakpoints exempt, since custom properties can't be used there).

**D15. Vitest everywhere.** Angular 22 and Nest 12 both default to it. API e2e tests run serially against `orbot_test`, which each suite resets (refused for any database not ending in `_test`).

**D16. Glossary lives in `packages/shared/src/glossary.ts`** (not a YAML file as first planned), so API and web share one typed source.

**D17. Search snippets are plain text.** `ts_headline` marks matches with `⟦…⟧`; the web app splits on those and renders `<mark>` itself, so record content is never interpreted as HTML.

**D18. Phase 1 screens beyond the bare shell.** ORBAT, Unit, Bot, Task, Archive (search + history/diff/as-of), Sitreps (read-only feed) and a Needs-you list are built minimally on the real API, because the Phase 1 test ("every step can be found in the record") is best demonstrated in the UI. Phase 2 polishes them (inline approvals, command palette, tree view).

**D19. Rogue scenarios ship with the runtime.** `rogue-leak` and `rogue-crash` exist to prove principle 5 end-to-end; they're harmless (the redactor masks them) and useful for demonstrating redaction.

## Phase 2

**D20. Overseers think through `BotRuntime`.** Overseers are bots (settled decision), so planning (`draftBackbrief`), curation (`curate`) and cold-start checks (`assessColdStart`) are runtime methods. `SimulatedRuntime` answers them with deterministic rules (`runtime/simulated-overseer.ts`); `ClaudeRuntime` will use the model. Nothing outside `runtime/` knows which brain is in use.

**D21. The Field Manual is a set of versioned entries.** Each lesson is an `fm-entry` with its own history and provenance (`sources`: handover id + version, commander, git, cold-start). Merging a repeated lesson adds a source instead of a duplicate; retiring sets `retired: true` (a new version), which moves it to the archive tier — search treats a retired entity's current version as archived. The unit's `field-manual` document is re-rendered from active entries in the same transaction, so whole-document history/diff/as-of keep working. That document cannot be rewritten as a blob (400 with a pointer to entries).

**D22. Only general lessons are promoted automatically.** The simulated Overseer promotes `flagsForSuccessor` items that don't name a specific task, branch or "yet"; task-specific notes and tried-and-failed items stay in the handover, which a successor on the same task is briefed with anyway. This keeps the Field Manual from filling with noise.

**D23. Unit documents in git, one-way mirror plus import.** `UnitDocumentStore` (interface) / `GitDocumentStore` writes `.orbot/units/<slug>/` on an `orbot/unit-docs` branch of the unit's first connected repository, via its own worktree, committing each batch of changes (coalesced per unit). Field Manual sections carry hidden `<!-- fm:<id> -->` markers so human edits map back to entries; standing orders carry `<!-- so:<id> -->`. `sync()` imports human edits as new versions by `system:git-import` and runs before every briefing. War Diary files are read-only (events are immutable); edits are restored and reported. Units without a repository simply have no mirror. Pushing the branch upstream is a Phase 4 connections concern.

**D24. Approval gates.** `approve-everything` and `backbriefs-and-deploys` both hold backbriefs for the Commander; `escalations-only` auto-approves (decision recorded as `auto-approved` by the Overseer). Deploy gating arrives with Logistics in Phase 4.

**D25. Commander → unit missions are a temporary shortcut.** Until HQ exists (Phase 4), the Commander gives a mission straight to a unit's Overseer (`POST /missions`, "New mission" on the unit view). Missions may have `operationId: null`.

**D26. Dispatch only what the Overseer issued.** Tasks created from an approved backbrief carry `autoStart: true` and are started by the Overseer's dispatcher whenever their bot is idle. Tasks issued directly by the Commander are started by hand ("Start task"), which keeps the Commander in control of ad-hoc work.

**D27. Reject = re-plan in place.** Sending a backbrief back writes a `rejected` version with the note, then the Overseer writes the next round as a new version of the same backbrief (round + 1, notes carried forward). History shows every round.

**D28. Approvals have no Undo.** Approving issues tasks that may start at once; a reversing entry can't un-run work. The toast says so. Field Manual, standing-order and document edits do have Undo (a new version restoring the old text; retire is undone by reinstating).

**D29. Background work is serialized per unit.** Bus-driven reactions (plan, curate, dispatch, after-task sitreps, docs mirror) run through `Background`, one job at a time per key, so an Overseer never acts on a half-applied change. Tests and the seed wait on `settled()` (no pending jobs, no running bots).

**D30. "A fresh bot" is proven, not assumed.** The `relay` scenario's second half reads only the brief: it blocks if the handover or the Field Manual convention is missing. The Phase 2 test runs it with the documents, then twice with them withheld (handover; Field Manual + search), and both controls block naming what's missing. The only thing a successor inherits physically is the branch.

**D31. Unit view sections are navigation, not tabs.** Overview / Field Manual / War Diary / Handovers / Rules / Supply are links (`?section=`) with `aria-current`, so each is deep-linkable and the back button works.

**D32. Keyboard.** Ctrl/⌘+K command palette (ARIA combobox + listbox, CDK dialog focus trap); `g` then `o/a/s/r/p/,` to go to screens; `?` for the cheat sheet. Shortcuts are ignored while typing in a field, except Ctrl/⌘+K.

## Phase 3

**D33. The Overseer interprets chat through `BotRuntime.interpret`.** It returns an `Interpretation` (zod-validated): message kinds, typed `ChatAction`s, musings, missing supply, an answer, and anything unclear. `SimulatedRuntime` uses a deterministic sentence-by-sentence rules/keyword classifier (`runtime/simulated-interpreter.ts`), so chat works offline and in tests. HQ has no Overseer bot until Phase 4, so the HQ channel is read by the default runtime, acting as `system:hq`.

**D34. Chat can only emit a closed set of actions.** `create-mission`, `withdraw-mission`, `frago` (stand down / amend), `resume`, `rule-change`, `supply-grant`, `supply-revoke`, `budget-grant`, `grant-deploy-rights`. Each runs through `ActionsService`, which calls the same services the UI uses, and returns a summary, links and its inverse. Chat has no side doors.

**D35. Orders log = append-only `orders.log` events.** Each records the originating message, the action, the summary, links and the inverse. Undo runs the inverse and appends a new entry with `reverses`; a second undo is refused. Some changes have no inverse (deploy rights; withdrawing a mission) and say so instead of offering Undo. Undoing a mission order withdraws it (`withdrawn` mission status, backbrief rejected, tasks stood down).

**D36. Orders reach live work in two ways.** Running bots get a recorded `frago` that `TaskRunner` delivers into the run (`RunContext.waitForFrago`), and they re-read live orders with `RunContext.orders()`. Blocked tasks whose block reason shares at least two significant words with what changed are restarted by the Overseer (with a unit sitrep). New tasks pick up changes from their brief.

**D37. A rule change replaces only the best-matching order.** "Stop blocking on low-severity findings" removes the standing order that best matches it, not every order that mentions findings. Ties are removed together.

**D38. Musings and irreversible orders are held as `pending.action` events.** Musings get "Yes, do it" / "No"; irreversible kinds (the setting `irreversibleActions`, default `grant-deploy-rights`) need the typed phrase (setting `confirmationPhrase`, default "confirm"). Answers are `pending.resolved` events. Settings are a versioned `settings` entity.

**D39. Cross-unit orders are relayed by HQ.** An order naming another unit runs against that unit, is logged with `routedVia: 'hq'`, and HQ posts it into the other unit's channel. The full HQ (planning, routing, shared record) comes in Phase 4.

**D40. Production deploy rights are given only by order in chat.** The Supply Depot screen lists production environments but issues them only through chat, where the irreversible-order confirmation lives.

**D41. Toasts live in the CDK overlay container.** When a dialog (chat drawer, palette) is open, CDK hides everything outside the overlay container from assistive tech; toasts must stay announced and clickable, so the outlet moves itself there.

**D42. The chat history is a plain scrolling log, not virtual-scrolled.** Messages vary a lot in height (read-back cards), the view loads the last 500 per channel, and full history is in the record and Archive. Virtual scroll stays on the fixed-row feeds (working record, War Diary, sitreps).

**D43. Docs mirror writes are serialized per repository.** Units that share a repository share its `orbot/unit-docs` worktree, so `GitDocumentStore` runs one git operation at a time per repository.

## Phase 4

**D44. HQ is a service, not a bot.** `HqService` runs operations as `system:hq`; its staff work (planning, after-action) goes through the default runtime's `planOperation` / `afterAction`, so it stays runtime-agnostic and works offline.

**D45. One integration branch per operation.** `orbot/op-<id8>` is cut from the repository's default branch. Every task in the operation starts from it (`baseRef`); finished work and fix tasks are merged back in, so each unit receives exactly what the previous one delivered. Branches and worktrees are never removed.

**D46. Missions in an operation form a chain.** The plan creates build → inspect → guard → deploy missions linked by `dependsOnMissionId`. Downstream missions sit in `waiting` until the upstream mission hands off. Units brief back before execution, and execution starts only when every backbrief is approved.

**D47. A send-back is a task stood down with "Sent back: …".** HQ turns it into a fix task in the upstream unit, preferring a bot that is free. The downstream mission waits, and the sent-back task is re-queued when the fix is integrated. In simulation, `inspect-strict` always sends back once and adds a handover flag aimed at Engineers, so the loop is exercised every time.

**D48. Production deploys need two things.** The Commander's approval on the deploy task (shown inline on Approvals and the operation page; skipped only when the unit's gate is escalations-only), and production deploy rights for the unit, which are given only by order in chat (D40). Without rights the deploy task blocks, and granting them resumes it.

**D49. After Action review lessons become standing orders automatically.** The AAR is written as a document; each lesson becomes a standing order in the unit it names (or every unit in the operation), as a new unit version attributed to `system:hq` with the review as its reason, so the Commander can see and revise it. Cross-unit lessons (handover flags naming another unit) are posted as HQ sitreps and land in the operation's shared record document.

**D50. ClaudeRuntime is a manual tool loop on the Messages API, not the Agent SDK.** ORBOT must own every side effect: file access is confined to the task worktree, scripts are limited to `npm run`, commits go through git, and every tool call becomes a record event via `RunContext`. No tool returns a secret value. A handover is required before any terminal tool (done/blocked/failed/send_back/stand_down). Overseer and HQ calls use structured outputs (zod), validated again by ORBOT. Server-side fallback is enabled. The runtime is registered only when `ANTHROPIC_API_KEY` is set, and the key is added to the redactor.

**D51. Bots can be switched between runtimes** (`PUT /bots/:id/runtime`, a select on the bot page with Undo). The choice is a versioned field on the bot.

**D52. Launching an operation from chat has no inverse.** Withdrawing a whole operation is done by standing its units down (Phase 5), not by Undo.

## Phase 5

**D53. Stand down is an order on a target, not a status.** A `halt` field (`reason`, `by`, `at`) on a bot or a unit, or on settings for "everything". Each is a versioned change with who and why; lifting it is another version. Bot and task statuses stay what they are: a halted bot is idle, and its paused task is `stood-down` with the reason "Stood down by order: …". Lifting an order resumes exactly those tasks. (The older "stood-down" bot status still means retired by replacement.)

**D54. Work pauses with a handover even if the bot doesn't write one.** `TaskRunner.stop` aborts the run. If the bot left no handover this run, ORBOT writes one from the run's own record: the last steps, the branch to pick up from, and a flag to check uncommitted changes. The paused task's next brief carries it, as for any successor.

**D55. Three layers keep halted work halted.** The Overseer's dispatcher skips halted units and bots. `TaskRunner.start` asks the policy hook (`task.start`), and the `Stand down` policy rule refuses it, with the refusal on the record. The same rule refuses every bot event mid-run, so a run caught between the order and the abort finishes as stood down, not blocked.

**D56. Stand down by chat is reversible.** `stand-down` and `lift-stand-down` are each other's inverse in the orders log. "Stand down" with no particular work named halts the addressed unit; "everyone/everything" halts all units; a callsign halts that bot. "Stand down the mobile layout" is still a frago on that work. HQ planning and Overseer backbriefs continue during a stand-down: it stops work, not thinking.

**D57. The banner is the single place to see every order in force.** It shows on every screen, with a Resume button per order. The header has "Stand down all units" (it asks for a reason). Unit and bot pages have their own Stand down / Resume. Each action gives an Undo toast.

**D58. Budget caps: three levels, one source of truth.** A unit's cap is its existing `computeBudget` (0 means no cap; the seed gives each unit 100). An operation's cap is `budgetUnits`, set when stating intent or on the operation page. A task's cap is its own `budget.limitUnits`. Spend is always the sum of `cost` events in the record (by unit, operation or task), never a counter kept on the side.

**D59. The cost is recorded first, then the run stops.** A bot reports a cost after spending it, so ORBOT never refuses to record a cost. Right after each cost, `TaskRunner` asks the policy hook (`task.continue`). At a cap, the `Budget cap` rule refuses, and the task is blocked with "Held by policy: Compute budget cap reached: …". So a unit can end slightly over its cap, by at most one bot step. The same rule refuses `task.start` at a cap.

**D60. The warning fires once per crossing.** When a cost takes spend across the warning share (setting `budgetWarnAt`, default 80%), ORBOT writes a `budget.warning` event and a unit sitrep. While spend stays at or above the share (and at the cap), the ORBAT, Approvals and the operation page show a Needs-you item.

**D61. Raising a cap releases exactly the work it held.** Setting a cap (unit page, operation page, or in chat: "Give Engineers 20 more compute budget") restarts blocked tasks whose reason is the budget cap, in that unit or operation. Each restart goes through the policy check again, so work still over another cap stays held. A `budget.set` event records the change and the tasks it released. A simulated bot picking up held work skips a commit it already made.

**D62. Escalation climbs a fixed chain: Overseer → HQ → Commander.** Each level's step is an `escalation` event (same `chainId`): what that level saw and what it did, plus a sitrep at Overseer and HQ level. The Commander's step stays open as a Needs-you item, with Acknowledge, until the work moves on (the task is picked up again or done, or the stood-down bot resumes) or the Commander acknowledges it. Closing it is an `escalation.resolved` event.

**D63. What counts as stuck, and what the Overseer does first** (thresholds are settings):

- **Stall:** no entry on the task's record for `stallSeconds`. The Overseer first sends a status-check frago. Still silent for another `stallSeconds`, it stops the run (paused with a handover) and escalates.
- **Timeout:** one run longer than `timeoutSeconds`. It is stopped with a handover and escalated.
- **Repeated failure:** a task that has failed `repeatedFailures` times is not retried. It is escalated, and the escalation replaces the plain "failed" item for that task.
- **Failing bot:** a bot whose last `failingBotRuns` runs all failed is stood down by its Overseer and escalated.

A single failure is not an escalation: it already shows as a failed task, and a failure is usually a judgement that needs the Commander anyway. The sweep runs every `ORBOT_ESCALATION_SWEEP_SECONDS` (tests call it directly).

**D64. HQ has no remedy of its own yet.** It records that it saw the escalation and raises it to the Commander. Moving work to another unit is left for later (Deconfliction / Main Effort).

**D65. Deconfliction: the map comes from git, the notices go on the record.** Each task already has its own worktree and branch (`orbot/task-<n>`). "Who touches what" is worked out from git on demand: the files each active task (queued, working, blocked, stood-down, awaiting approval) changes since it branched, committed or not. ORBOT's own per-task notes under `orbot/` are left out. Nothing is cached that could drift from the branches.

**D66. HQ informs; it does not block.** When a task writes or commits a file that another active task in the same repository is also changing, HQ records one `deconfliction` notice per pair of tasks (and per new file), posts an HQ sitrep, and sends both running bots a frago naming the other task. Both keep working: whichever lands second rebases. Tasks in the same operation are not flagged against each other, because they land in order on the operation's integration branch.

**D67. Separation of duties is enforced where every write lands, not at each door.** `RecordService` runs write guards before any entity version is stored. `DutiesService` registers one: if the actor is a bot, it refuses the bot doing any of these to itself or its own unit, by whatever path the write comes:

- approving a backbrief or a production deploy (its own work, or its own unit's);
- changing its own unit's standing orders, ROE or approval gate;
- adding supply, budget or credentials to itself or its unit;
- lifting a stand-down that covers it.

The refusal is a policy decision on the record ("Separation of duties: …", action `duty:<kind>`), and the write is rolled back. The Commander, HQ and other system actors are not bots and are not limited by this. Bots acting on other units are not "their own" and are left to the other rules.

**D68. On "escalations only", HQ approves plans on the Commander's behalf.** Before, the Overseer that wrote the plan also approved it. Now `system:hq` does, so no bot approves its own work. The Commander still sees every approval on the record.

**D69. Disputes are raised by bots about their own task, and the task waits.** A `dispute` bot event (a scenario step, or the ClaudeRuntime `raise_dispute` tool) names the other unit and states the claim. The task blocks ("Disputed with Guard: …"), and a versioned `dispute` entity opens.

**D70. HQ rules only under standing orders.** `BotRuntime.ruleDispute` decides who prevails and cites the orders that settle it. ORBOT keeps only citations of orders that really exist on the two units, and a ruling without one is treated as no ruling. If an order settles it, the ruling takes effect at once: the task resumes with the ruling in its brief (`TaskBrief.rulings`) and the bot follows it. If none does, HQ refers it to the Commander (a Needs-you item) and the task stays blocked.

**D71. The Commander has final say over any dispute.** The Commander can rule on a referred dispute, or uphold or overturn an HQ ruling. That ruling is final: a second ruling is refused, and the way to change course is a new order. An overturn reaches the work in progress: a blocked task resumes with the final ruling, and a running one gets a frago. If the work is already done, the ruling is on the record, and acting on it is a new order.

**D72. Links from the API keep their fragments.** Attention links like `/disputes#dispute-…` go through a `url` pipe (Router.parseUrl) so `routerLink` doesn't encode the `#`. This also fixes the backbrief links in Needs you.

**D73. The main effort is one operation, named by the Commander.** The build prompt names the feature but doesn't define it. Taking the military meaning, the main effort is the one effort everyone else supports. In ORBOT that is one operation at a time, because operations are HQ's level and the Commander's statements of intent. It is a versioned field on settings (`mainEffort`: operation, reason, by, at), so every change has who, when and why. It is set from the operation page, by chat through HQ ("Make Gatekeeper the main effort", with Undo), or by `PUT /api/main-effort`. Closing the operation clears it (by `system:hq`). A bot can't set it: that counts as changing its own rules (D67).

**D74. The main effort goes first; supporting work makes way, but the Commander's own work doesn't.** Overseers dispatch each bot's main-effort tasks before the rest of its queue, and unit and bot queues are shown in that order. If a main-effort task is ready but its bot is busy, the Overseer moves it to a free bot in the same unit. If no bot is free, a bot on supporting work that an Overseer dispatched pauses with a handover ("Made way for the main effort: …"). That task goes back in the queue and picks up from its handover once a bot is free. A pause costs the paused work a restart, so it is a setting (`mainEffortYield`, on by default). Work the Commander started directly is never paused for it: that was a direct order.

**D75. The main effort changes priority, not limits.** Budget caps, stand-down orders, approval gates and separation of duties apply to main-effort work exactly as to any other. Bots never cross units for it, because a bot belongs to one unit. Moving work between units stays a Commander's order.

**D76. Recon is a read-only task that files a report with the unit.** The build prompt names Recon without defining it. ORBOT takes it as reconnaissance before committing: a bot surveys the code to answer a question. It is a task (kind `recon`), so it gets a bot, a worktree, a brief, a War Diary and a handover like any other work. Its output is a `recon` document owned by the unit, not the bot (principle 3), and later work that shares enough words with it is briefed with it (`TaskBrief.recon`, at most two reports). You order one from the unit page (Recon…), in chat ("Recon the payments repo: how are card numbers stored?", with Undo calling it off) or with `POST /api/recon`. The unit's least busy free bot takes it.

**D77. Read-only is enforced, not just asked for.** A policy rule refuses any artifact (a file or a commit) from a recon task, and the task is held ("Recon is read-only"). ClaudeRuntime gives recon tasks no tool that changes the workspace (no write_file, run_script, commit or send_back) and refuses them if called anyway. A recon's worktree is never integrated.

**D78. HQ can recon before planning.** "Recon first" in the intent dialog (`reconFirst` on the operation) makes HQ send the unit that would build it to recon the intent. The O Group waits for the report and passes it to the planner (`OperationPlanInput.recon`). If the recon fails, HQ plans without it and says so.

**D79. The sand table is HQ rehearsing the plan against the record, with no model.** The build prompt names it without defining it. ORBOT takes it as a rehearsal: before the work is done for real, HQ walks the operation's handoff chain mission by mission. For each unit it checks bots that can work, stand-downs, the Overseer, work already queued, blocked tasks and standing orders that can hold work up. It also checks deploy rights for the deploy stage, the approvals you will be asked for, and the budgets. It lists blockers, risks and notes, each with what to do and a link. The checks are deterministic, so a rehearsal is free, repeatable and the same on every runtime. It changes nothing. Each rehearsal is kept as a `sand-table` event, so earlier ones stay on the record.

**D80. HQ rehearses at the O Group and again when execution starts; the result advises, it doesn't stop.** A no-go appears in the operation's Needs you and as an HQ sitrep. The Commander decides whether to go ahead: the sand table never blocks an approval or holds work, because deciding is the Commander's job (chain of command). The cost estimate is the plan's tasks (or what's left of them) times the unit's average spend per finished task, or 4 units when the unit has no history. You can also rehearse from the operation page or in chat ("Rehearse Ledger on the sand table").

**D81. The daily brief is a dated document HQ writes at a set time.** Settings hold the time and time zone (`dailyBrief`: on, 07:00, UTC by default). HQ checks every `ORBOT_DAILY_BRIEF_CHECK_SECONDS` (60) and writes the day's brief once it is past that local time. It covers the last 24 hours:

- what needs you;
- each operation (with the main effort marked);
- a table of units: status, done, failed, blocked, spend against budget;
- what happened: deploys, escalations to you, stand-downs, HQ sitreps;
- what was learned: new Field Manual entries and recon reports;
- what is queued.

There is one `daily-brief` document per local date, so writing it again that day ("Write today's brief now") revises the same document, and every earlier brief is kept. It is composed from the record by rule, with no model, so it is free and always the same shape.

**D82. Phone alerts are an HTTP push to a URL kept in the secrets store.** The build prompt asks for phone alerts. ORBOT sends them the way ntfy works: POST the text, with Title, Priority, Tags and Click (a deep link into ORBOT) headers. ntfy's free phone apps receive them, and any service that takes such a POST works too. Web Push was ruled out because it needs VAPID keys, a service worker and an installed app before the first alert. Whoever has a push topic URL can read the alerts, so the URL is a secret. It is stored as a credential and referenced in Settings by name only, and it appears in no record, log or response; `alert.sent` events keep the credential's name, the redacted text and whether delivery worked. You choose which kinds alert you: escalations reaching you, plans and production deploys waiting for approval, disputes referred to you, work held at a budget cap, a sand-table no-go, and the daily brief. Each event alerts once, and the alert text goes through the redaction layer.

**D83. A service record is worked out from the record; it is about conduct, never knowledge.** Each bot's page shows:

- when it joined, and whom it replaced or was replaced by (`replacesBotId`, now set when a bot is replaced);
- its runs and how they ended, success rate, average run length and compute spent;
- what it wrote (handovers, diary entries, sitreps, reports), and its disputes, escalations and policy refusals;
- **commendations**: Field Manual entries that came from its handovers;
- a timeline of notable entries.

It is computed on request from events and versions, so there is no second copy to drift. It never goes into a brief and no Overseer decision reads it. A bot's successor learns from the unit's documents, not from another bot's history (principle 3). A replaced bot's record stays on its page.

**D84. Three ranks: Commander, Captain, Observer.** The build prompt asks for "other officers (multi-user with ranks)". Ranks only matter for what each one may order, so there are three. A **Commander** commands everything: the passphrase holder, and any officer appointed at that rank. A **Captain** commands the units the Commander assigns them: missions, tasks, plans and deploys to approve, standing orders, the Field Manual, recon, standing their units down, adding bots, acknowledging their escalations. An **Observer** reads everything and can ask questions in chat, but gives no orders. Some things stay with a Commander whatever the unit: supply, budgets and deploy rights (from the depot); operations and the main effort (HQ's level); disputes (the Commander has final say); settings; officers.

**D85. Officers are versioned `officer` entities; passwords live only in the secrets store.** An officer has a name, a login, a rank and (for Captains) units. Their password is hashed with scrypt and stored as a secret named `officer-login.<id>`. That keeps it off the record and out of every response (principle 5). It is hidden from the Supply Depot, and it can never be handed to a bot or used as an alert URL. Officers are retired, never deleted (principle 4). Retiring one ends their session on their next request and closes their live-update connection, because the sign-in check reads the officer from the record each time. Officers act as `officer:<id>` on the record, so every approval and order shows who gave it. Chat shows other officers' messages under their names.

**D86. Rank is checked on every write, and the default is Commander-only.** A global `AuthorityGuard` runs after sign-in. Reads are open to every rank. A write route has to declare `@Authority(...)` to open itself to Captains, and a `unit` rule names the units the request acts on. A route with no declaration is the Commander's alone, so a new route can't be opened to Captains by accident. Chat checks each order the same way. An order outside the officer's command is read back as "Not done: … — Captain Ada does not command Guard." and changes nothing, while the rest of the message goes ahead. Confirming a held order and Undo are checked too. The web hides controls the officer can't use (`*orbCan`), but the server is what enforces it.

**D87. Connections are supply: a GitHub connection per repository, behind a provider interface.** The build prompt asks for a code host, an issue tracker and a build pipeline. A connection is a depot item (`spec.kind: 'connection'`) for one of the depot's repositories. It has an API URL (GitHub or GitHub Enterprise), owner and repository names, a push URL, and the token as a credential used by name. Switches choose what it is used for: code host, issue tracker, build pipeline. Only GitHub is built; the `Connector` interface (verify, pull requests, issues, pipeline result) is what a GitLab or Jira adapter would implement. Connecting checks the repository can be reached with the token. A push URL with a token in it is refused. Disconnecting is a new version (`connected: false`), so the history stays.

**D88. What each connection does.**

- **Code host.** After each integration, HQ pushes the operation's integration branch and opens one pull request for it. The token goes to git through the environment (`GIT_CONFIG_*`), never in a URL or an argument. A finished task can be opened as a pull request on demand.
- **Build pipeline.** The result for each pushed commit (GitHub check runs, falling back to commit statuses) is recorded as `pipeline.status`. Pending results are checked every `ORBOT_CONNECTIONS_POLL_SECONDS`, or on demand. A failure on an operation's branch sends a fix task to the building unit.
- **Production deploys.** A policy rule holds them ("The build pipeline is not green: …") until the pipeline has passed on the commit being deployed. The deploy then goes ahead by itself. This follows "nothing ships with a known failure".
- **Issue tracker.** Open issues are listed on the Connections page. Taking one on makes a mission: the issue title is the goal, and its checklist (or "Issue #N is resolved") is the definition of done. This also works in chat ("Take on issue #7"). When the mission is done, HQ comments on the issue and closes it (a per-connection setting). Issue text from outside is redacted before it is recorded.

**D89. Connecting and disconnecting are the Commander's; using a connection follows rank.** Opening a task's pull request and taking an issue on for a unit need command of that unit. Checking pipelines needs any order-giving officer.

**D90. Reads fill in defaults for fields added since a version was written.** Bodies are validated on write. Without this, a database from an earlier phase would return settings without `alerts`, operations without `pullRequest`, and so on. Reads now run each body through its schema to apply defaults. A version that no longer fits the schema is returned exactly as stored. Nothing is rewritten, so the record stays append-only (principle 4).

**D91. A `claude-code` runtime runs bots on the Commander's own Claude plan.** The Commander asked to run ORBOT on their Claude subscription rather than an API key. The `claude-code` runtime uses the official Claude Agent SDK, which drives the Claude Code binary signed in with the `claude` login on this machine (or `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`). It shares its tools, prompts and Overseer/HQ structured outputs with the API runtime (`ClaudeFamilyRuntime`), so the record looks the same whichever one ran.

- **Same confinement as the API runtime.** The bot gets only ORBOT's tools, served in-process over MCP. It gets none of Claude Code's built-in tools (no shell, no file access outside the worktree tools), no settings, hooks or CLAUDE.md from the machine, and no saved sessions. Anything not on ORBOT's tool list is denied.
- **The process gets an allow-listed environment.** It sees only what it needs to run and find the login. ORBOT's keys and passwords stay behind (principle 5), and so does `ANTHROPIC_API_KEY`, because if Claude Code saw one it would bill the API instead of the plan.
- **Plan problems block, they don't fail.** A usage limit, a missing login or a billing problem blocks the task with what to do next ("Resume the task when it resets…"), because it is not the bot's fault.
- **Turning it on.** Set `ORBOT_CLAUDE_CODE=on`, or `ORBOT_RUNTIME=claude-code` to make it HQ's runtime too. Settings has "Run every bot on…" to switch the whole force at once (`PUT /api/bots/runtime`); each bot's switch is a new version with the reason.
- **For one Commander's own use.** Anthropic's terms allow a Pro/Max login for ordinary individual use. They don't allow it to serve other people. While other officers give orders, use the API runtime. Settings says so when `claude-code` is chosen.

**D92. Servers: bots log in over SSH to the servers their unit holds, and set them up as they see fit.** The Commander wants bots to use their SSH keys to log in to Linux servers and set them up. A server is an environment with SSH access (`spec.server`: host, port, user, key credential, pinned host keys, optional URL). Issuing it to a unit is what lets that unit's bots in, the same way supply works everywhere else.

- **Connecting** (`POST /api/supply/servers`, the Commander's) does three things: it scans the server's host keys and pins them, it logs in with the key to prove access, and it shows the fingerprints in the depot. From then on ORBOT talks to that machine only (`StrictHostKeyChecking=yes` against the pinned keys). "Check login" in the depot tries again.
- **Bots** get `list_servers`, `server_run` (a non-interactive shell command as the configured user) and `server_upload` (copies the task's committed HEAD into a directory, recorded as a `deployment`). What to install and how to configure it is the bot's judgement, guided by its brief. Its prompt asks it to document what it set up in the War Diary and its handover, so the knowledge stays with the unit (principle 3).
- **Secrets.** The private key lives in the secrets store and is used by name. For each command it is written to a private temporary file, used, and deleted. ssh runs with no agent, no user ssh config and an empty environment. The bot never sees the key. Every command, its exit code and its redacted output (the tail) are on the record as `server.command`, alongside a `credential.used` entry.
- **The redactor now leaves SSH public keys and `SHA256:` fingerprints alone.** They are public by design, and masking them broke host-key pinning. Private keys are still caught by the private-key pattern and by exact match.
- **Production servers** are reached only inside a production deploy task the Commander approved. A policy rule ("Production servers") refuses every other attempt, and the refusal is on the record. Staging servers are open to the holding unit's work. Recon gets no server commands (read-only).
- **Out of scope for now:** keys with a passphrase (store a dedicated key without one), interactive sessions, and `sudo` that asks for a password. Bots use `sudo -n`, so give the server user passwordless sudo if they should install packages.

**D93. Dev servers: bots build, test and iterate on the Commander's own Linux servers.** The Commander asked for dev servers where bots check out code and run whatever they need. They chose their own servers over per-task containers. A dev server is a server environment (D92) with tier `dev`.

- **Each bot gets its own folder**, `~/orbot-dev/<repository>/<bot>`. A bot works one task at a time, so the folder is never shared mid-task. What it installed there (dependencies, build caches) is still there for its next task on the same repository.
- **The workspace stays the work of record.** Bots edit in their git worktree as before. `dev_run` first brings the folder up to date with the working tree, uncommitted edits included, then runs the command there. The sync uses rsync where the server has it: deletions follow the tree, and `.git` and gitignored paths such as `node_modules` are left alone. Otherwise it uses a tar of the tree's files, which carries no deletions. ORBOT checks for rsync when the server is connected. `dev_fetch` copies generated files (a lockfile, generated code) back into the workspace, where they are committed like any edit. Commits, handovers, deconfliction and integration all keep working from git, unchanged.
- **Access works as for every server.** The unit must hold the dev server. The key is used by name. Each command, with the bot's folder, its exit code and its redacted output, is on the record as `server.command`. `server` may be left empty for the unit's first dev server. Recon may use `dev_run`, since building and testing change no code, but not `dev_fetch`.

**D94. The Supply Depot is split into sections, and its forms are dialogs.** One long page had grown a tab bar of forms above a mixed list of everything. Now `?section=` picks Repositories, Credentials, Servers & environments or Connections (in the order you set things up: a server's key is stored first), each with its count, its own list and its own "add" button. The forms open as dialogs, so a refusal (an unreachable server, a bad name) shows in the form with nothing typed lost. `?connect=` from a read-back opens the right section with its form filled in. Each item shows what it is and how it is reached (location, login, pinned host keys, what a connection is used as), and the issue and withdraw controls are shown only to whoever may order them (supply is the Commander's).

**D95. Apps on servers: installed from `deploy/apps` by ORBOT, not by bots.** The Commander wants to add a server, open it, and install apps and resources on it: vLLM first, later an API built in one of the depot's repositories. An app is a folder in `deploy/apps/<id>`: a manifest (`app.json`: settings, secrets, what it provides) and `install.sh`, `status.sh`, `uninstall.sh`. The scripts are kept in this repository so they are reviewed and versioned like the rest of ORBOT.

- **Installing is the Commander's**, from the server's page. ORBOT copies the app to `/opt/orbot`, writes its settings and secrets to a root-only env file over SSH stdin (never on a command line), and starts `install.sh` as root under `systemd-run`, so an install that downloads tens of gigabytes keeps going if ORBOT restarts or the connection drops. ORBOT follows the state file the script writes (`running <step>`, `done`, `failed <step>: <why>`) every `ORBOT_APPS_POLL_SECONDS`, records `app.install` events with the redacted log tail, and shows the live log on the page. Reading progress is not recorded (it is a read); every command that changes the server is a `server.command` event.
- **Apps run in Docker, managed by systemd.** The installer checks for the NVIDIA driver (it never installs one: that needs a reboot), installs Docker and the NVIDIA Container Toolkit if they are missing, and needs passwordless sudo.
- **What an app provides becomes supply.** vLLM provides a `model`: an OpenAI-compatible base URL, the served model name, the context window and the API key, which ORBOT generates and stores as a credential (kept across reinstalls). "Check it answers" asks `/v1/models` with the key. Removing the app marks the model not connected; nothing is deleted.
- **Settings are checked against the manifest** before anything runs: types, ranges, and a character set that keeps them safe in a shell env file.

**D96. The bot workspace keeps bots away from the apps on a shared server.** The Commander's GPU server is both a dev box for bots and the home of production services (vLLM now, their own APIs later), and they asked for separate users. A server's page offers "Set up bot workspace": ORBOT creates `orbot-dev` (no sudo, not in the docker group, in `video`/`render` for the GPU), generates its SSH key and stores it as a credential. From then on `dev_run`/`dev_fetch` log in as `orbot-dev`. A policy rule refuses bots the admin login (`server_run`, `server_upload`, and dev work before the workspace exists) on any server that runs apps, except inside a production deploy the Commander approved, which is how a unit's own API will be deployed there.

**D97. Environments and servers can be edited; a server's login and host key are guarded.** Edit (on every environment's card, and on a server's page) changes the name, tier, host, port, user, key and URL as a new version. A new host, port, user or key is tested by logging in before anything is saved, so a typo cannot cut ORBOT off. Host keys are pinned again only for a new host or port, or when the Commander ticks "the server was reinstalled": otherwise a changed host key is still refused, which is the point of pinning. The tier cannot move to or from production while a unit holds the server, since that would give or take deploy rights without the confirmation production needs (D92). Models served from the server follow it to a new host. A plain environment (connected before servers existed, or without SSH) becomes a server by giving it a login in the same form: its host keys are pinned and the login proved as on connect, and it keeps its id and history. A server cannot go back to being a plain environment, and a dev environment is always a server (`PUT /api/supply/environments/:id`).

**D98. Rules of engagement are briefed, and a bot asks permission before doing what they say it must escalate.** A unit's rules of engagement (`mayDoAlone`, `mustEscalate`) go into every bot's brief and `check_orders`, so they bind the bot rather than only describing the unit. Before doing something under "must escalate", a bot writes a handover and calls `request_permission` (action, the rule it falls under, why). The task becomes `awaiting-approval` with the request on it (`task.permission`, `permission.requested`), the bot keeps the task, and it appears in Needs you and as a phone alert. The Commander, or a Captain of the unit, decides it in Needs you, on the task page or in chat (`decide-permission`; a refusal must say why). Either way the task resumes straight away with the decision in its brief (`permission.decided` events): approved, the bot goes ahead; refused, it finds another way or reports blocked. We chose this over two alternatives. A policy rule that matches bot actions against the free-text rules could not judge intent reliably, and limits that must hold whatever the bot thinks stay hard policy rules (production only inside an approved deploy, a red pipeline, recon is read-only). Sending requests to the Overseer to decide would put a model in charge of the very decisions the rules hold back for people. The separation-of-duties guard refuses any bot that decides a request its own unit made. A decision cannot be undone in chat (no inverse): the bot acts on it at once.

**D99. A server's health check: login, apps, disks, on demand.** The Commander wants to see on a server's page that ORBOT can still log in, that the installed apps run, and how much disk is left. "Run health check" (and opening the page, when the last check is over 10 minutes old and the viewer is the Commander) logs in with the server's key, and as the bot workspace user if there is one; runs each running app's `status.sh` and, for an app that serves a model, asks the model from ORBOT's side too; and reads free space with `deploy/server/disk.sh` on `/`, `/home`, Docker's storage and ORBOT's app data (model weights). A disk is degraded at 85% used or under 5 GB free, down at 95%. The result is one `server.health` event (healthy, degraded or down, the worst part deciding); nothing on the server changes, so the reads are not recorded command by command. The status vocabulary gains Healthy, Degraded and Down. The web dev server no longer pre-bundles `@orbot/shared`, so a change to it (like these statuses) reaches the browser without clearing Angular's cache.

**D100. Operations have resources, and missing ones block them.** The Commander wants every operation to have the resources it works with, one or more repositories above all, and an operation without them to be blocked; assignable from chat and the web alike (and, later, by voice, which will use the same chat actions).

- **Resources are depot items assigned to the operation** (`supplyIds`, in the order given; the first repository is where work is handed off and deployed from). They can be named when stating intent (the form's resource picker; in chat "…, using payments-service"), and assigned or taken off later on the operation's page or in chat ("Use gpu1 for Operation Ledger", "Take gpu1 off Operation Ledger"). The chat orders are `assign-resource` / `release-resource` (each the other's Undo), Commander only, routed through HQ.
- **Needs come from the plan.** An operation always needs a repository; a plan with a deploy mission needs a production environment; HQ's planner may add others (a GPU dev server, a model, a staging environment, a credential), marked optional when nice to have. A need is met by an assigned, connected item of the right kind and tier (a server also counts as an environment).
- **A missing required need holds the operation at the O Group.** Without a repository HQ does not even plan (recon and planning need somewhere to look). Once planned, the plan is kept on the operation, so assigning what was missing does not plan it again: HQ checks and issues the missions at once. While it waits, a sitrep names what is missing and the operation shows in Needs you (HQ's item, `unitId: null`) and on its page.
- **Units get what the operation has.** When missions are issued (and when something is assigned later), every unit in the chain is issued the operation's resources, except a production environment: that is deploy rights, still given by order with confirmation (D33). The integration branch is opened in every repository; a backbrief may aim a task at any of the operation's repositories, and its work is integrated, and sent back, in that repository. Handoffs, the pull request and the deploy still use the first repository; spreading those across repositories is the next step.
- **Taking off** never touches units (they keep what they were issued) and refuses the first repository once missions are out.

**D101. A held task does not hold its bot.** Before, a bot whose task blocked (or asked permission) stayed `blocked` with that task, and the Overseer only dispatches idle bots, so the rest of its queue, from any operation, waited for the decision. A unit whose bots had all hit something sat idle while its missions still read "working". Now:

- **Blocked or awaiting a decision:** the task keeps its bot and its worktree, and the bot goes back to `idle` and takes its next task. The Needs-you item is the task's (`blocked-bot`, keyed by the task). This changes D98's "the bot keeps the task": the work still resumes from the handover and the task's own worktree.
- **Resuming** (a frago, a permission decision, a dispute ruling, a raised budget cap, a green pipeline) goes through `TaskRunner.resume`: it starts at once if the bot is free, or goes first in the bot's queue (made auto-start) and the Overseer starts it when the bot finishes. The policy check runs either way, so a task still held stays blocked.
- **A bot that itself crashed** stays `failed` with its task (it needs replacing), but the Overseer moves the rest of its queue to the unit's bots that can work, shortest queue first.
- Each dispatch frees any bot still holding a held task, and each Overseer dispatches once at start-up, so units stuck before this change move on after a restart.

**D102. An operation's course can change: another main repository, or cancel.** The first repository assigned is the operation's main one: where its work lands, is handed off and deploys from. Assigning another repository only adds it, so "change the repo from A to B" needs its own order.

- **Set main repository** (`set-main-repository`; the operation page's "Make main"; `POST /operations/:id/resources/main`) moves the repository to the front. Before the O Group, that is all. Once missions are out, HQ withdraws them, re-plans nothing, and issues the same plan again on the new repository (for an operation planned before plans were kept, the withdrawn missions are the plan). Withdrawing stops running work with a handover, stands down waiting work (including a deploy awaiting approval), rejects pending backbriefs and marks the missions `withdrawn`; their ids are kept in `withdrawnMissionIds`. Each unit then briefs back afresh. What was done stays on the old repository's branches and on the record (principle 4). The old repository is then an ordinary resource and can be taken off. It has no Undo: changing back issues the missions afresh again.
- **Cancel** (`cancel-operation`; "Cancel operation…"; `POST /operations/:id/cancel`) withdraws the missions the same way and closes the operation with `cancelled` (who, why, when), without an After Action review.
- In chat, both need the typed confirmation whenever work would be thrown away (always for cancel; for a new main repository once missions are out), whatever the settings' irreversible list says.

**D103. The code is on show: every commit and diff, tied to the record.** Logs say what a bot did; the diff shows it. `CodeService` (`apps/api/src/code/`) reads the depot's repositories with git, read-only, and never stores what it reads: the repository is the copy of record for code, so a second copy in the record could only drift.

- **Views:** a repository's history on any of its branches (default, operations' integration branches, tasks' branches; `GET /repositories/:id/history?ref=`), one commit with its diff (a merge against its first parent, so an integration shows what it brought in; `GET /repositories/:id/commits/:sha`), a commit by id alone, found in whichever repository has it (`GET /commits/:sha`), and a task's changes (its commits, the whole diff since its base, and what is in its worktree but not committed yet; `GET /tasks/:id/changes`).
- **Tied to the record:** each commit's origin comes from the events that already name it: a bot's `artifact` commit (task, bot, unit, operation), or HQ's `integration`, `handoff` and `deployment`. Nothing new is written when a bot commits.
- **In the web:** the task page has "Code changes". Every commit, integration, handoff and deployment entry in a working record links to its commit (`/commits/:sha` moves to the commit's full address under its repository). Repositories in the Supply Depot link to their history.
- **Limits:** diffs are cut short past 200 files, 1,500 lines a file or 20,000 lines in all, and say so. Binary files are named, not shown. A branch must be one the repository has, so nothing but a real branch name reaches git.
- **Secrets:** a value a bot puts in code is masked in every diff by the response redaction layer, like any other response (`secret-leak.e2e-spec.ts` commits one and checks every view).

**D104. A project can be one HTML file, deployed by ORBOT with no server.** The Commander wants to start a project whose whole deployment is a single HTML file. Three pieces, each an ordinary depot item afterwards:

- **A repository from a template** (`POST /api/supply/repositories/new`; "Start a new one from a template" in the depot's repository dialog). ORBOT creates it under the workspaces' `source` folder, writes the template (`single-html`: `index.html` and a README stating the rules; `empty`: a README), makes the first commit and connects it like any other. The shape is kept on the depot item (`RepositorySupply.project`: kind and entry file), so it reaches every bot's brief (`TaskBrief.repository`), the Overseer's backbrief input and HQ's planner: no build step, no server, nothing fetched from another origin, everything inline in the one file, and a deploy that publishes that file. The rules live in the repository's README too, where a human reads them.
- **A static site** is an environment with no server (`GenericSupply.site`: the folder ORBOT publishes into and the entry file; `site: true` on `POST /api/supply/environments`). It meets a plan's "production environment" need like a server does, and deploy rights to it are issued the same way (D33). `SitesService.publish` (bot tool `publish`; the simulated `deploy` step uses it when the unit holds a site named, or of the tier, it deploys to) takes files from HEAD of the task's branch with `git archive`, unpacks them into a new folder under `versions/`, points `current` at it, and records a `deployment` event with the URL (the operation's `deployment.url`); the depot item keeps the last publication. A policy rule ("Production sites") allows a production site only inside an approved deploy, as for servers, and refuses recon. Every publication is kept (principle 4).
- **Serving.** `GET /api/sites/:id/` serves the current publication to anyone (a deployed product is for its users), with a Content-Security-Policy that sandboxes it: an opaque origin, so the page cannot read ORBOT's cookies or call its API as the viewer, and `connect-src 'none'`, so it can reach no other origin either, which is the project's own rule. Only what was published is served (no other version, nothing outside the site). `GET /api/sites/:id/download` gives the entry file as a download named after the site.
- **One order starts all of it:** `POST /api/projects` ("New project" on the Operations page; in chat, "Start a new project called Ledger: a ledger that works offline") makes the repository and the site (`<name> site`, production), issues the site to a unit if the Commander confirms deploy rights, and with an intent launches the operation with both assigned, so HQ plans at once. Nothing is deleted: the chat order has no Undo.

We chose a static site over pushing to GitHub Pages or an outside host (a connection can do that later) because it needs nothing but ORBOT itself, and over serving the file on a separate origin because the sandbox gives the same isolation at one address.

**D105. ORBOT runs as production software: one image, one origin, Docker Compose.** The Commander wants to deploy ORBOT somewhere and use it daily. The image (`Dockerfile`) builds the shared package, the API and the web app, and the API serves the web build itself when `ORBOT_WEB_DIST` is set: one origin, so no CORS and a first-party session cookie. `docker-compose.prod.yml` runs Postgres (no published port), the API (loopback only, `ORBOT_TRUST_PROXY=on`) and, under the `tls` profile, Caddy with automatic HTTPS for `ORBOT_DOMAIN`. `docs/deploy.md` is the runbook.

- **Safe by default.** With `NODE_ENV=production` the config refuses the compose file's placeholder passwords and a plain-http origin other than localhost, naming the setting to fix. The session cookie is `Secure` whenever the origin is https (`ORBOT_COOKIE_SECURE=auto`). Every response carries `nosniff`, `Referrer-Policy`, `X-Frame-Options: DENY`, a minimal `Permissions-Policy`, HSTS when secure, and the web app a Content-Security-Policy (`script-src 'self'` plus the hash of Angular's one inline script; `frame-ancestors 'none'`). A handler that serves other HTML sets its own policy: the middleware fills one in only when the response has none. The live feed accepts the configured web origin only.
- **Sign-in is throttled** in memory per address: ten failures, then fifteen minutes (HTTP 429 with a plain message). Addresses are never written to the record.
- **`GET /api/health`** asks both databases and answers up or down with the version, never why: a connection error names hosts and users.
- **Seeding has modes.** `ORBOT_SEED=force` (the container's default) creates the four units with their Overseers, bots and Field Manuals and nothing else, so the Commander connects their own repositories; `demo` is what `npm run dev` does; `none` leaves the record empty.
- **Backups** are `scripts/backup.sh` (both databases with `pg_dump`, plus the workspaces: clones, document mirrors, published sites) and `scripts/restore.sh`, which replaces them and therefore asks twice. The secrets dump is only readable with `ORBOT_SECRETS_KEY`; the runbook says to keep the two apart from the server.

**D106. The hold policy: what a bot fixes alone, what it records, and what holds the work for the Commander, set per unit and per operation.** The Commander first ruled a fixed rule for Guard (record everything; fix small findings; low never holds; a high finding needing large changes holds), then asked for it to be theirs to set: per unit, per operation, with an automatic mode in which nothing ever holds.

- **The setting** (`HoldPolicy`, `packages/shared/src/domain/hold-policy.ts`): `fixUpTo` (none, small, medium, large: how big a fix a bot may make on its own) and `holdFrom` (low, medium, high, critical: the severity from which an unfixed finding holds the work; `never` is the automatic mode). Default: small fixes, hold from high. `UnitBody.holdPolicy` is the unit's; `OperationBody.holdPolicy` overrides it for that operation's work (null = each unit's own). `decideFinding(policy, severity, fix)` is the one rule: fix, record, or hold.
- **Where it acts.** It is briefed, not enforced: judging a finding's severity and a fix's size is the bot's call, and the record shows what it decided and why. `BriefingService` puts the effective policy in every brief; the Claude runtime states it in words for every task and tells check tasks to record findings with severity and what was done. The simulated runtime has a `finding` step that applies the policy deterministically (`guard-check`: a low finding with a small fix; `guard-check-blocker`: a high one with a large fix, held by default, recorded in automatic mode). Guard's seeded standing orders now refer to the policy rather than fixing numbers (knowledge belongs to the unit; the Commander changes orders in chat).
- **Where it is set.** The unit's Rules tab and the operation's page ("What holds the work"; `PUT /units/:id/hold-policy`, `PUT /operations/:id/hold-policy`, the Commander's alone, and a bot changing its own unit's policy is refused by the separation-of-duties guard). In chat: "Hold only on critical findings", "Go fully automatic", "Only record findings", "Operation Ledger: automatic", "Operation Ledger: back to the units' own settings" (`hold-policy`, undone by restoring the previous policy).
- The demo keeps a tightened standing order on Guard ("Low-severity findings also block release."), added by the demo seed only, because the demo chat exists to show an order being lifted.

**D107. An order given in chat is already approved.** The Commander ordered a fix in chat, and the Overseer's plan for it then waited in Approvals. The approval gate exists for work HQ plans from an intent; a mission the Commander (or an officer with the rank) orders in chat, or an issue taken on in chat, carries `preApproved`, and the Overseer's backbrief goes ahead at once (approved by HQ on the Commander's behalf, never by the Overseer that wrote it). Uncertainty is handled before the order exists: unclear messages are read back as questions, hedged ones as proposals to confirm, irreversible ones with the typed phrase.

**D108. The chat keeps its context.** "Say the word and I'll do that" followed by "Do it" got "I can't tell what that refers to": the interpreter saw only the current message. Now the channel's recent turns (`InterpretInput.history`: what the Commander said, what the Overseer answered and proposed) go with every message, and the Claude interpreter is told that a short reply refers to its last proposal, and to put proposals in `musings` (typed actions the Commander confirms) rather than only in prose. Independently of the runtime, `ChatService` treats "Do it", "Yes", "Go ahead" as confirming the open proposals from the channel's last read-back, through the same path as the confirm button; an irreversible proposal still needs its typed phrase.

**D109. The simulated runtime is not installed in production.** Scripted bots exist for development, demos and tests. The Commander found their production force running on them: the seed had put every bot on the simulator whatever `ORBOT_RUNTIME` said, and the runtime was always installed, so the Settings page offered it and nothing refused it. Now the force seed uses the configured runtime (only the demo's bots play scenarios), and `ORBOT_SIMULATED=auto` installs the simulator in development but, in production, only when `ORBOT_RUNTIME=simulated` is the Commander's own choice for trying the command system (`on` forces it, `off` removes it). Without it, no bot can be switched to it, the demo seed refuses with a message, and a bot left on it from before fails its task with "No bot runtime called simulated is installed", which the Commander fixes in Settings.

**D110. A task picked up again restarts its branch when the integrated work conflicts with it.** A Guard review sent the work back; Engineers rebuilt it; the review was queued again and could not start: merging the integration branch into the review's own branch conflicted (both had added a `package.json`), and the worktree was left mid-merge, so every resume failed the same way. Now `WorkspaceManager` aborts any half-done merge first, tries the merge, and on a conflict keeps the branch's commits (and anything uncommitted, committed first) on `<branch>-kept-<sha>`, resets the task branch to the integrated work, and reports it: a `workspace.prepared` event with `restarted` (the files that conflicted, the kept branch), a unit sitrep, and a line in the bot's brief telling it where its earlier work is. Nothing is lost (principle 4), and a re-check always starts from what was actually integrated, which is what a check is for.

**D111. **D112. Every hold names its way out.** The Commander found a task held by a Guard finding, pressed Resume, and watched it hold again with the same words; a failed task said "git merge failed: Command failed: …" and nothing else, with no Retry. ORBOT's errors already say what happened and what to do next (`{ code, message, action }`); the record of a task that stops short now does the same. `statusAction` goes with `statusReason` (and `action` with the `task.status` event): the bot's own suggestion when it gave one (the `blocked` and `failed` tools take an `action`; scenarios too), else the usual way out for a hold, a failure or a crash, with a policy refusal's own `action` when that is what held it.
